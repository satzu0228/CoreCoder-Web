## 阶段 0：打通「输入 → 流式回复」的最短闭环

**完成时间**：2026-08-06
**对应提交**：`5d0b34c` feat: corecoder web - stage 0 streaming chat closure（本地已提交，未推送）

### 实际改动

- `corecoder/web/server.py` — `run_web(agent)`：先用一个探测 socket 拿空闲端口再关掉（和 Jupyter 同款做法，TOCTOU 窗口在本地单用户场景可接受），uvicorn 起在后台线程，轮询 `server.started` 后才打开浏览器，主线程阻塞等 Ctrl+C。
- `corecoder/web/app.py` — `create_app(agent, token)`：FastAPI 实例挂一个全局单例 `Agent`（单 workspace 假设下安全），中间件校验 token（header `X-CoreCoder-Token` 或 query `?token=`），`/` 路径豁免（首页要先加载才能从 URL 里读到 token）。
- `corecoder/web/routes/chat.py` — `POST /api/chat`：核心桥接逻辑。`agent.chat()` 是同步阻塞调用，`on_token` 回调也是同步触发的，用一个后台线程跑 `agent.chat()`，配合 `queue.Queue` 把 token 事件中转给 async 生成器，再包成 SSE frame 吐给 `StreamingResponse`。`queue.get()` 本身阻塞，套了一层 `run_in_threadpool` 避免卡住 event loop。
- `corecoder/web/static/index.html` — 单文件原生 JS 前端，没上 Vue 工程化（按计划，阶段 0 只验证链路）。`fetch` + `ReadableStream` 手写解析 SSE，因为 `EventSource` 不支持带 body 的 POST。
- `corecoder/cli.py` — 在 `main()` 最前面拦截 `sys.argv[1] == "web"`，分流到新增的 `_main_web()`，独立的 argparse（只接 `-m`/`--base-url`/`--api-key`），不接受 `-p`/`-r`（需求文档 1 节要求）。顺手把原来内联在 `main()` 里的"未找到 API key"报错文案提成 `_print_missing_api_key()`，两条路径复用。
- `pyproject.toml` — 加 `fastapi>=0.115,<1.0`、`uvicorn>=0.30,<1.0`。
- `tests/test_web.py` — 6 个测试，用 `ScriptedLLM` 不需要真实 API key：首页公开访问、无 token/错 token 返回 403、SSE 流内容正确、agent 抛异常时流不崩而是发 `error` 事件、token 走 query 参数也认。

### 没碰的地方

`agent.py`/`llm.py`/`context.py`/`session.py` 零改动，符合开发计划的硬约束。这一阶段没有引入事件总线（`events.py`）、没有 `tool_start`/`tool_end` 可视化——按计划这些是阶段 1 的内容，阶段 0 只验证纯文本流式对话这一条最短链路。

### 验证方式

1. `pytest tests/test_web.py` 6 个全过，`pytest tests/` 全量跑（Windows 下一些 tmp_path 权限问题是环境既有问题，跟这次改动无关）。
2. `ruff check` 只剩一处故意保留的 `except Exception`（chat.py 里把 agent 执行异常转成 SSE `error` 事件而不让流崩掉，和 `agent.py` 里 `_exec_tool` 的既有宽松捕获风格一致）。
3. **真实端到端**：本地配置 `.env` 接 DeepSeek，跑 `corecoder web`，浏览器手动验证过一轮对话；另外用 curl 直接打 `/api/chat`，验证了纯文本流式回复和触发 `bash` 工具调用两种场景，SSE 事件序列都正确，token/403 校验也生效。

### 和计划的出入

- 计划里提到"阶段 0 不建 events.py"——严格照做了，`tool_start` 目前完全没有对接到 Web 层（`on_tool` 回调在 web 路径上是空的），工具调用过程在网页上现在是不可见的，只能看到最终文本结果。这是预期内的，阶段 1 补。

## 阶段 1：工具调用过程可视化

**完成时间**：2026-08-06

### 实际改动

- **新增 `corecoder/web/events.py`** — 模块级事件总线，三个函数：`set_emitter(fn)` 注入推送函数、`clear_emitter()` 清除、`emit(event_type, data)` 发事件。`_sse_emit` 是进程级单例，符合"单用户单 workspace"的 MVP 前提。线程安全性依赖注入的函数本身（`queue.Queue.put` 是线程安全的），这里不加额外锁。

- **改造 `corecoder/agent.py`**：
  - `on_tool` 回调签名从 `(name, args)` 扩展为 `(tool_id, name, args)`，让前端能用同一个 id 把 `tool_start` 和 `tool_end` 配对。这是对调用方（`cli.py` 的 REPL 路径和 `routes/chat.py`）的破坏性变更，两处都同步更新了。
  - 单工具路径：`_exec_tool` 返回后、`messages.append` 之前，加一行 `events.emit("tool_end", {"id": tc.id, "name": tc.name, "result": result})`。
  - 并行路径 `_exec_tools_parallel`：把 `[f.result() for f in futures]` 改为 `concurrent.futures.as_completed` 逐 future 到达逐个发 `tool_end`，结果存进 `dict[tc.id -> result]`，最后按原始 `tool_calls` 顺序重组列表返回，确保调用方 `zip(tool_calls, results)` 不乱序。这解决了需求文档 3.1 节指出的"并发工具最慢那个完成才一起到达前端"的问题。

- **改造 `corecoder/web/routes/chat.py`**：worker 线程启动前 `set_emitter(push)`，`finally` 块 `clear_emitter()`，确保每个请求用自己的 queue、不跨请求污染。`on_tool` 回调把 `tool_start` 事件推进同一条 queue（而非另起一条路径），`push` 函数统一格式为 `{type, ...data}`，和 `on_token` 推的 `{type: "token", text}` 格式对齐。

- **改造 `corecoder/web/static/index.html`**：在回复块下方动态生成卡片式时间线（`<ul class="timeline">`，纯原生 JS，不上 Vue）。`tool_start` 到达时插入一张黄边 `running` 卡片，`tool_end` 到达时按 `id` 找到对应卡片标为绿边 `done`，结果默认折叠，点「▶ show result」展开。时间线只在有工具调用时出现，纯文本回复不产生空 `<ul>`。

### 没碰的地方

`llm.py`、`context.py`、`session.py`、其他工具（`read.py`、`bash.py`、`edit.py` 等）零改动。`confirm_registry.py`、`routes/confirm.py`、确认机制均未涉及——按计划这些是阶段 2 的内容。

### 验证方式

1. `python -m compileall -q corecoder` 无输出（无编译错误）。
2. `python -c "from corecoder.web.events import ...; from corecoder.agent import Agent; from corecoder.web.routes.chat import router"` 全部 import 成功。
3. `pytest tests/ -q`：68 个测试通过，17 个 ERROR 全部是 Windows `tmp_path` 权限问题（`PermissionError: [WinError 5]`），是环境既有问题，与本次改动无关。

### 和计划的出入

- **`cli.py` 的 `on_tool` 回调需同步更新**：计划里只提到改 `agent.py` 和 `routes/chat.py`，但 `on_tool` 签名变成三参数后，`cli.py` 里 REPL 路径原来传的两参数 lambda 会在运行时报 `TypeError`。改动时顺手对齐了，没有遗留 breakage。
- **并行路径的 `tool_end` 顺序**：需求文档 3.1 节提到"按每个工具各发一次，不能等全部收集完再一起发"，但没提返回值的顺序问题。`as_completed` 的到达顺序和原始 `tool_calls` 顺序不一定一致，如果直接 `return [fut.result() for fut in as_completed(...)]` 会导致 `messages` 里 `tool_call_id` 对应错乱。用 `dict` 按 `tc.id` 收集、最后按原始顺序重组，解决了这个隐患。

## 阶段 2：`edit_file` 人机协作确认闭环（MVP 核心）

**完成时间**：2026-08-06
**对应提交**：`23aaf7a` feat: corecoder web - stage 2 edit_file human-in-the-loop confirmation

### 实际改动

- **新增 `corecoder/web/confirm_registry.py`** — `ConfirmRegistry` 类 + 模块级单例 `registry`。核心是 `dict[event_id -> threading.Event]` + `dict[event_id -> bool]` 两张表，`create()` 生成 `uuid4().hex` 的 id 并注册一个 `Event`；`wait()` 在锁外 `ev.wait(timeout=300)`（锁外等，`resolve()` 才能拿到锁去 `set()`），返回前**无条件**清理 `_events` 和 `_results` 两条记录——超时和正常返回都清理，不残留脏状态；`resolve()` 对已超时/不存在的 id 返回 `False`，让路由能据此回 4xx。线程安全靠一把 `threading.Lock` 保护两张表。

- **改造 `corecoder/tools/edit.py`**：
  - 把 `_unified_diff(...)` 的调用从"写入后"挪到 `write_text` 之前（需求文档 3.2 第一步的关键改动点），diff 在写入前就生成好。
  - 生成 diff 后走 `registry.create()` → `events.emit("confirm_required", {id, action: "edit_file", file_path, diff})` → `registry.wait(event_id, timeout=300)` 三步。
  - `approved=False` 时返回 `f"Edit rejected by user.\n{diff}"`——**不进** `except Exception` 分支，和参数错误/执行错误在语义上区分开（需求文档 3.3），LLM 能理解"用户拒绝了"而不是"工具报错了"。
  - 只有 `approved=True` 才真正 `write_text` 并记入 `_changed_files`。

- **新增 `corecoder/web/routes/confirm.py`** — `POST /api/confirm`，body `{id, approve}`，调 `registry.resolve()`；返回 `False`（超时/不存在）时抛 `HTTPException(404)`，避免前端重试/误发时静默成功或 500。

- **`corecoder/web/app.py`** — `include_router(confirm_router)`，让 token 鉴权中间件同样覆盖 `/api/confirm`。

- **`corecoder/web/static/index.html`** — 新增 `ConfirmModal`：收到 `confirm_required` SSE 事件后弹窗，按 `action` 区分标题（`edit_file` → "Confirm Edit" / `bash` → "Confirm Command"），展示文件路径或命令文本 + `<pre>` 纯文本 diff（Monaco 留到阶段 4）。「Approve」/「Reject」按钮调 `/api/confirm`，成功后关弹窗。SSE 处理分支里加了 `confirm_required` 的 case。

### 没碰的地方

`bash.py` 未动——按计划阶段 3 才复用这套确认机制。`events.py`、`chat.py`、`agent.py` 零改动（`confirm_required` 直接复用阶段 1 建好的事件通道，`chat.py` 的 `push` 函数天然支持任意事件类型）。没有做 `ConfirmableTool` 抽象——按计划要等阶段 3 两个真实实现都落地后再判断是否值得抽。

### 验证方式

1. `python -m compileall -q corecoder` 编译检查通过，无语法错误。
2. `python -c "from corecoder.web.confirm_registry import registry; from corecoder.tools.edit import EditFileTool; from corecoder.web.routes.confirm import router"` 所有关键导入通过，模块化设计检查无误。
3. `pytest tests/` 全量：69 个测试通过，26 个 ERROR 全部是 Windows `tmp_path` 权限问题（`PermissionError: [WinError 5]`），是环境既有问题，与本次改动无关。
4. 代码审查：`ConfirmRegistry.wait()` 和 `resolve()` 的并发逻辑——锁外等待、锁内管理状态、无条件清理，符合设计要求；`edit.py` 的确认流程——diff 前置、事件发射、等待批准、拒绝返回区分出 `rejected by user` 语义；路由返回 404 而非隐默处理已超时的 id。

### 和计划的出入

- **`edit.py` 的 `except Exception` 兜底范围**：计划里强调"拒绝要区分于报错"，实现时把 `registry.wait()` 放在 `try` 块内。如果 `wait()` 本身抛异常（理论上不会，但防御性考虑），会落进 `except Exception` 返回 `Error: ...`——不过正常拒绝路径返回的是 `Edit rejected by user.`，语义区分是成立的。这个兜底和 `agent.py` 里 `_exec_tool` 的既有宽松捕获风格一致。
- **前端弹窗期间 SSE 连接**：计划提到"等待确认期间 SSE 连接不能断"。实现上 `confirm_required` 事件到达后前端只是弹窗，SSE 的 `reader.read()` 循环继续挂着等下一个事件，没有主动断开；用户点按钮走的是独立的 `/api/confirm` 请求，和 SSE 流互不干扰。这个点没有额外代码，靠的是阶段 0 就定好的"SSE 单向 + 确认走独立 POST"的架构。
- **超时清理的验证**：计划验收标准里没提超时场景，但 `wait()` 的"无条件清理"是设计里明确要保证的（防止脏状态累积）。手动验证了超时后 `_events`/`_results` 都被清掉，`resolve` 对已清理的 id 返回 False 走 404。

## 阶段 4：bash 命令确认 + 三态结果 + 页面刷新恢复

**完成时间**：2026-08-06

### 实际改动

**核心设计决策**：
1. 使用 `web/_confirmable.py` 辅助函数而不是 `ConfirmableTool` 基类（避免提前修改 Tool 体系）
2. `registry.wait()` 返回 `ConfirmResult` 三态枚举，区分 APPROVED/REJECTED/TIMEOUT
3. 保持 `_check_dangerous()` 职责不变，只在 `bash.execute()` 中接入确认流程
4. CLI 兼容性：检查 `events._sse_emit` 是否为 None 决定走确认还是直接拒绝

- **改造 `corecoder/web/confirm_registry.py`**：
  - 新增 `ConfirmResult` 枚举（APPROVED / REJECTED / TIMEOUT）
  - `create(payload: dict)` 现在接收完整 payload 并存储（用于页面刷新恢复）
  - `wait()` 返回 `ConfirmResult` 而非 bool
  - `resolve()` 内部转换 bool 为 ConfirmResult
  - 新增 `get_pending()` 方法查询当前待确认状态

- **新增 `corecoder/web/_confirmable.py`**：
  - 纯函数 `request_bash_confirmation(command, reason)` 包装确认流程
  - 调用方在 bash.py 中使用，减少重复代码
  - 返回 ConfirmResult 便于区分用户决策

- **改造 `corecoder/tools/bash.py`**：
  - 导入 `request_bash_confirmation` 和 `ConfirmResult`，使用 try/except 防止 CLI 版本导入失败
  - 危险命令检测逻辑不变，改变是后续处理：
    - 如果 `events._sse_emit` 为 None（CLI 模式），直接拒绝
    - 否则（Web 模式）调用 `request_bash_confirmation()` 获得 ConfirmResult
    - 根据结果返回不同消息：APPROVED 继续执行，REJECTED 返回拒绝消息，TIMEOUT 返回超时消息
  - 普通命令（未命中黑名单）无感知，直接执行

- **改造 `corecoder/tools/edit.py`**：
  - 改用 ConfirmResult 三态而非 bool
  - 新增 TIMEOUT 分支消息，让 LLM 区分超时与拒绝
