# waq的corecoder学习记录

## 1、agent

### 1.1 工具调用函数_exec_tool

拿到tool calls，不是立即调用工具函数，先bind验证参数是否正确，这样调用出错可以区分是模型给的参数不对还是工具内部本身有问题

### 1.2 用户中断输出，但是有的工具的调用结果还没返回怎么处理

_answer_pending_tool_calls函数。遍历tool calls，找出有tool call但是没有回答的tool，在它们的toolmessage里填上[interrupted]，这样toolmessage不会为空，下一次请求不会报错

## 2、tool

一个工具，由名字、给大模型看的描述、描述参数的 JSON Schema和真正执行逻辑的execute的组成.所有工具继承自一个基类。

### 2.1 edit_file 搜索替换

先判断是不是UTF-8编码
模型给工具要被替换的原文，要换上的新文，工具要判断原文在文件里的出现次数，只有恰好出现一次才替换。出现多次工具不确定要换哪一处，那就告诉模型这段原文出现了多次，让模型重新拓展原文，直到原文在文件里是唯一的

### 2.2 bash

危险命令检测。建立一个危险命令名单，执行前检测在不在名单里，是危险操作就不执行。

## 3、llm

### 3.1怎么在流式输出里，把工具调用用到的参数拼起来

一个调用的 JSON 参数会被切成好几个碎片，分散在多个 chunk 里到达，怎么拼成完整 JSON？
使用一个以 `index` 为 key 的字典缓存不同工具调用的数据
每收到一个 chunk，先判断其中是否包含 `tool_calls`。如果存在工具调用信息，则获取 `tc_delta.index`：
	如果字典中不存在该 `index`，说明是第一次收到这个工具调用的碎片，需要初始化一个缓存对象，保存 `id`、`name` 和参数字符串 `args`。
	如果已经存在，说明这是同一个工具调用后续返回的碎片，将新的 `id`、`name` 信息补充，并通过 `+=` 将参数字符串继续拼接。
等流式响应结束后，再对每个 `index` 对应的完整参数字符串执行 `json.loads()`，转换成真正的参数字典，最终得到完整的 Tool Call。
如果loads下来一个不合法的json，就把它回退成一个空的{}，然后在工具调用的时候处理参数错误

### 3.2 token是怎么算出来的

在请求里加一个 `stream_options`：

```python
params["stream_options"] = {"include_usage": True}
```

加了这个，provider 会在流的最后一个 chunk 里带回 `usage`，里头有 `prompt_tokens` 和 `completion_tokens`。
然后查表乘以价格，llm.py里有一张按百万 token 计价的表（输入价、输出价）

### 3.3 重试逻辑

_call_with_retry：
限流、超时、连接错误这类瞬时错误和服务端错误可以重试，每次重试的等待时间：指数退避 是上一次的2倍 ；客户端错误不重试
stream_options：有些供应商不支持这个参数，捕获 `BadRequestError`（400），把 `stream_options` 去掉再试一次

## 4、 context

maybe_compress估算用了多少token，然后根据token选择不同的处理方法
至于 token 怎么估的，`estimate_tokens` 粗糙估计：字符数除以 3。

```
self._snip_at = int(max_tokens * 0.50)      # 50% -> 截断臃肿的工具输出
self._summarize_at = int(max_tokens * 0.70)  # 70% -> LLM 摘要旧对话
self._collapse_at = int(max_tokens * 0.90)   # 90% -> 硬折叠，最后手段
```

**第一层 self._snip_at 旧的工具输出，是有保质期的**

不调模型，纯文本处理，把超过 1500 字符的**工具结果**，截成只留头三行和尾三行

**第二层：self._summarize_at 让模型给旧对话写个摘要**

把旧的对话整段交给模型写一个摘要，只留最近 8 条消息原样不动。

**孤儿 tool 消息**

只剩tool消息，tool calls被压缩没了。
在切分前，把边界往前挪，直到边界那条消息不再是 tool。

**第三层：self._collapse_at 最后手段**

保留最后几条消息加一个摘要，其余全部折叠掉。它同样走 `_safe_split` 保证不留孤儿

## 5、并行执行与子 agent

### 5.1工具并行执行

单个就直接跑，多个就交给 `_exec_tools_parallel`，一个线程池，最多 8 个线程并发，每个跑一个工具，最后按原顺序收齐结果。

**共享可变状态的处理**

多个bash并行，共享同一个目录，会错乱：
把这种「每个执行流各自的状态」隔离开，别让它们共享。Python 里现成的工具是 `threading.local()`，线程局部存储，它给每个线程一份独立的副本。

### 5.2 子agent

派一个有独立上下文的分身去干活，返回给主agent结论。主 agent 造一个新的 `Agent`，共享同一个 LLM，但有它自己全新的 `messages` 列表。构造 agent 时，把每个 `AgentTool` 的「父指针」指回自己
子agent不准调用孙agent，把子agent的工具集里，去掉agentool

## 6、session and cli

### 6.1 REPL：一个对话循环套着一个对话循环

和agent循环（问模型、跑工具、把工具结果塞给模型）不同，这里的循环是读用户输入、交给 agent、打印回复、再读下一句。
**回调**

```python
response = agent.chat(
    user_input,
    on_token=on_token,
    on_tool=on_tool
)
```

`on_token` 让模型的文字一个个实时冒出来，打字机效果。`on_tool` 在每次调工具前打一行灰字，告诉你「它正要去读哪个文件、跑哪条命令」这两个回调是 agent 内核和界面之间唯一的耦合点，内核不关心你怎么显示，只在该出事件的时候喊一声，界面爱怎么呈现是界面的事。这种「内核出事件、外壳管呈现」的切分很干净，你想把 CoreCoder 嵌进别的程序（比如一个 web 服务），只要换掉这两个回调就行，内核一行不用动。第七篇会用到这个性质。

继续聊天：corecoder -r my_session
如果session_id用户输入了路径 就会造成路径穿越 需要对用户输入进行限制
**1.把 id 规整成一个安全的纯文件名**
**2.`_session_path` 把最终路径解析出来后，明确检查它的父目录就是会话目录本身**
